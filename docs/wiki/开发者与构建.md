**源码怎么编、测试跑什么、仓库怎么组织、发版怎么走。**

## 仓库结构：一个分支，多个目标

源码只有 **`main`** 一个分支，一次发版所有目标各出 Windows x64 / Linux x64 两个 jar。不按 Minecraft 版本或加载器分分支 —— 按分支划分时，非主力分支的更新依赖额外的「追平」提交，其时机不受任何机制约束，老版本因而长期滞后。

```
gradle.properties              # 仓库级身份：mod_version / mod_id / mod_group_id / license / authors
gradle/atomchat-layers.gradle  # 读身份 + 把 shared/ 与本目标挂载的层接进源集（各平台 apply 它）
versions/
  targets.json                 # 支持哪些目标（每个 MC 版本都要凑齐三个加载器，缺了要显式声明）
  layers.json                  # 有哪些层：三个轴 since / loader / mappings
  mapping-aliases.json         # 同一类在两家族上包路径不同的少数例外
  third-party-apis.json        # 共享层允许出现的第三方 API
shared/                        # 所有目标共用
layers/
  mapping/official/            # 官方映射家族共用（NeoForge + Forge）
  version/  loader/            # 版本层 / 加载器层（当前为空，见下文「为什么现在没有版本层」）
platforms/
  1.21.1-fabric/  1.21.1-neoforge/  1.20.1-forge/   # 各目标自己的代码 + 构建脚本 + 元数据 + 资源
tools/verify_targets.py        # 矩阵与身份的校验器（本地与 CI 跑同一份）
docs/                          # 平台文案 + 本 Wiki 的源
```

**根目录没有 `build.gradle`**：每个目标的工程目录自己一套构建（Fabric 用 fabric-loom、NeoForge 用 ModDevGradle、Forge 用 ForgeGradle），Gradle 版本与 Java 版本各不相同 —— 这是硬约束（ForgeGradle 6 不吃 Gradle 9；1.20.1 要 Java 17），所以不强行统一。

当前每个目标的规模：

| 工程 | main | test | 其中 |
|---|---:|---:|---|
| `shared/` | 103 | 57 | 三端共用 |
| `layers/mapping/official/` | 37 | 13 | NeoForge + Forge 共用 |
| `platforms/1.21.1-fabric/` | 60 | 16 | 含 48 个 Yarn 名孪生副本 |
| `platforms/1.21.1-neoforge/` | 23 | 3 | |
| `platforms/1.20.1-forge/` | 23 | 3 | |

## 构建与测试

在**目标自己的工程目录**里跑，不是仓库根：

```bash
cd platforms/1.21.1-neoforge
./gradlew build -Patomchat.nativePlatform=linux-x64 --no-daemon  # Linux: build/linux-x64/libs/
./gradlew build      # 构建 + 跑测试；产物在 platforms/1.21.1-neoforge/build/libs/
./gradlew runClient  # 开发环境启动（Fabric / Forge 目标同理）
./gradlew atomchatLayers   # 打印本目标挂了哪几层、接进来哪些源目录
```

- Fabric / NeoForge 目标用 **JDK 21**，Forge 1.20.1 目标用 **JDK 17**；
- Forge 目标会额外产出一个 `-slim` JAR（不内嵌依赖，仅供开发），**发版用不带 `-slim` 的那个**；
- 版本号只有仓库根 `gradle.properties` 一处，各平台不定义它（读不到直接失败，不给默认值）。

测试是 **JUnit 5**，只覆盖**纯逻辑层**（不需要启动游戏）：动画时长与缓动、布局数学、消息解析与分类、表情包存储、文件名清洗、AWT 状态判定、服务端表情迁移、@ 提及高亮、以及**字节格式本身**（`shared/src/test/resources/wire-goldens.txt` 是「抽出字节层之前」各端 codec 打出来的金标）。当前**每个目标各 505 项**（同一份测试对每个目标各跑一遍）。Windows 变体仍用 `skija-linux-x64` 测试域依赖支持 Linux CI；Linux 变体将同一原生库打包进产物。两个变体输出目录独立。商店每个系统使用独立文件/版本标签，Linux 标签追加 `-linux-x64`；玩家只安装其中一个。

## 分层规则

层的定义在 `versions/layers.json`，**一个层就是对目标的一个谓词**，三个轴：

| 轴 | 含义 | 层里不得出现 |
|---|---|---|
| `since` | Minecraft 版本不低于它 | 绑加载器、绑映射的构造 |
| `loader` | 这个加载器的目标才挂 | 绑版本、绑映射的构造 |
| `mappings` | 用这套映射名的目标才挂 | 绑版本、绑加载器的构造 |

目录由**声明的轴推出来**（`layers/mapping/official/`），没有第二处可以互相矛盾。挂载即声明：目标挂了自己满足不了的层，构建在**配置期**就红。

### 为什么现在没有版本层与加载器层

层的价值在于"同一个格子里的多个目标共用一份"。当前的格子：

| 格子 | 成员 |
|---|---|
| 1.21.1 + official | NeoForge（唯一） |
| 1.21.1 + yarn | Fabric（唯一） |
| 1.20.1 + official | Forge（唯一） |

每个格子只有一个成员，所以版本层与加载器层搬进去**不产生共享**，只是多一层目录。等出现同版本同加载器的第二个目标（例如 1.20.1-fabric）时，层才会自然长出来。

### 映射接缝（本仓刻意保留）

Fabric 用 Yarn、另两端用官方名。同一段逻辑因此有两套名字 —— 一份在 `layers/mapping/official/`（由两个 official 目标共用），一份是 Fabric 侧同路径的孪生副本。

代价要说清楚：**改到这些文件时，两套名字要各改一遍**。守卫能保证"孪生副本存在、路径一一对应、且不是逐字相同（那它本该进 `shared/`）"，但**保证不了两边逻辑一致** —— 那是手抄的固有风险，靠测试与 review 兜。

三个类因为要在原版包下访问包私有成员，Fabric 侧的路径与另一家族不同；这份差异写在 `versions/mapping-aliases.json` 里，孪生检查按别名去找。

## 校验闸

`tools/verify_targets.py` 本地与 CI 跑同一份，共 **13 条**，其中：

- **矩阵是规则**：每个出现过的 Minecraft 版本都要凑齐 Fabric / NeoForge / Forge 三条，缺了要么建、要么写 `buildable: false` 并说明为什么；
- **身份只有一份**：各平台不许自己定义 `mod_version` 等键；
- **工程目录与矩阵条目必须互相存在**：目录存在却不在矩阵里，等于一份没有任何地方编的源码；
- **谓词与挂载一致**：挂了自己满足不了的层 → 红；
- **孪生副本**：映射层里每个文件，另一个家族的每个在建目标都要有对应副本（按别名找）；少一个、或逐字相同 → 红；
- **声明与实现一致**：`targets.json` 里的 `java` / `gradle` 必须与工程的 toolchain / wrapper 相符；
- 另加：**访问扩宽覆盖一致**（三份 AW/AT 覆盖同一批成员）、**接缝清单新鲜度**（`shared/PLATFORM-SEAMS.md` 是生成物）、**资源落点**、**dist 隔离**（服务端侧的类不许引用客户端类型）、**别名完整性**、**共享层依赖面声明**，以及**共享层的 Java 级别闸**（`shared/` 必须能在最低那个目标的编译级别上编过 —— Java 17 上模式匹配 switch 还是预览特性，第一版 `Wire.write` 就栽在这里）。

## CI 与发版

| 工作流 | 触发 | 做什么 |
|---|---|---|
| `build.yml` | `main` 的 push / PR（`**.md` 与 `docs/**` 除外） | 读矩阵 → 三个目标各装对应 JDK 并 `./gradlew build`（含测试） |
| `release.yml` | 推 `v*` 标签 | **`vX.Y.Z`**：三个加载器分别构建 Windows x64 / Linux x64 变体 → 校验仓库版本号与标签一致 → 建一个 Release 挂六个 JAR → 发布到商店；**`vX.Y.Z-rc1`**：只建 prerelease，**不发布到商店** |

发版清单：

1. 改仓库根 `gradle.properties` 的 `mod_version`；
2. 在 `RELEASE_NOTES.md` 写 `## vX.Y.Z` 段落（发布说明由它摘出；标签带后缀时会回退到基础版本段落）；
3. 提交并推送 `main`；
4. 打标签 `vX.Y.Z` 并推送 → 看 `release.yml` 三段是否全绿。

只想演练流程、不想污染商店：打一个带后缀的标签（`vX.Y.Z-rc1`），商店那一段会被整段跳过。

> ⚠️ **演练只覆盖前三段**：`-rc` 标签会让 `publish` job 被 `if` 跳过，连它的 `matrix` 都不求值 ——
> 0.2.10 真发版时就栽在这里（`publish` 只声明 `needs: build` 却读 `needs.targets.outputs.list`，于是整个 job
> 被 GitHub 丢掉：run 标红、日志为空、jobs 列表少一个）。改 workflow 文件不够，**标签必须跟着走**
> （`git tag -f` + `git push --force origin vX.Y.Z`），因为 tag push 用的是标签那棵树里的文件。

### 商店发布与项目文案

| 商店 | 发布怎么走 | 项目文案怎么改 |
|---|---|---|
| CurseForge | `release.yml` 的 `:curseforge` 腿（curseforgegradle，`CURSEFORGE_TOKEN` 存在就跑） | **只能人工贴**：官方 Upload API 只有 `upload-file` / `update-file` / maven / 本地化四个端点，没有改描述的接口（[官方文档](https://support.curseforge.com/support/solutions/articles/9000197321-curseforge-api)）。文案真源是 `docs/curseforge-description.md` |
| Modrinth | `release.yml` 的 `:modrinth` 腿（minotaur）；需要 `gradle.properties` 里的 `modrinth_project_id` 与仓库 secret `MODRINTH_TOKEN`，缺任一条就是 SKIPPED | `python3 tools/store_sync.py`（默认**演练**，加 `--apply` 才发）→ `PATCH /v2/project/{id}`，**只改 `body` 一个字段**；也可以在 Actions 里手动跑 `同步商店文案` 工作流 |

`tools/test_store_sync.py` 用一个本地假 Modrinth 把这个脚本的每条分支跑一遍（什么时候发请求、发几个、发什么、什么时候不发、出错退出码），因为「令牌真的能用」这件事在本机验证不了，能验的就要验掉。
