# 0.8.0 渲染性能排查

日期：2026-11-15，主验收目标为 1.21.1-CCB。用户要求保留模糊、阴影、点阵、动态图与其他观感。本轮未启动 Minecraft，也未修改 AtomLib。

目前确认有 AC 绘制提交成本与 AtomLib 桥的固定边界成本；证据尚不足以把 CCB 整体掉帧单独归给其中一个。点阵批量提交只带来有限的组件收益，不能写成游戏 FPS 已改善。

## 实机样本

## 受控对照与实际修改

`V080RenderCostTest` 使用实际 AtomLib `SkijaRenderBridge` 和 AC 的 HUD、点阵代码，在隐藏的真实 OpenGL 上绘制 2560×1600 FBO。CPU 计时覆盖桥调用，GPU 计时使用实际查询；查询取回和清空 GPU 队列在 CPU 计时之外。没有 MC 世界、光影、原版批次或窗口呈现。

最初两轮桥 CPU p50 为 0.2932 / 0.2253 ms，HUD 整条路径为 0.5493 / 0.5170 ms，两条点阵为 1.4035 / 1.2910 ms。它们用于寻找成本方向，不作为后续不同负载轮次的性能基线。

优化前后的最终同轮对照均预录 Picture，避免把每帧 Java 绘制圆与 native 回放的差别冒充生产优化：

| 对照轮次 | 原点阵 Picture CPU p50 | 批量点阵 CPU p50 | 改善 |
| --- | --- | --- | --- |
| reference → batched | 3.3062 ms | 3.1297 ms | 5.3% |
| batched → reference | 3.6407 ms | 3.4180 ms | 6.1% |

桥的绝对成本在后续轮次发生较大漂移，因此仅报告同轮组件结果，不把这些数字外推为稳定的跨会话性能水平。原始输出保存于 `docs/evidence/2026-11-15-v080-followup/render-cost-gpu-parity.txt`。

`DotTexture.edgePoints` 将同一半径、颜色的内部点批量提交；渐隐侧边保持原圆命令。保留圆角裁剪、发光、透明度与采样方式，没有栅格贴图替换或降质。已有 CPU 字节对照覆盖裁剪、变换与多种主题色；真实 GPU 对照在 1、1.3、0.94 倍变换下逐字节相同。其他 GPU/驱动与 CCB 组合仍须实际复测。

## 动效和测量缺口

- 实际面板入口使用弹簧，而源码多处旧注释仍称指数缓动。其通用默认吸附条件允许位置余量 9%、速度小于 2 时直接跳到终点，存在提前收尾的离散步进；这是代码事实，不能据此排除帧耗时尖峰。
- 面板现在用独立的单调时间线：开 240 ms、关 180 ms，沿已有 cubic ease-out 连续取样；HUD 读同一时间线的互补进度。原切页曲线不改。
- 关闭仅捕获一次绘制命令，立即移除 Screen 并释放输入；之后 HUD 负责短暂退场。退场保留实时背景模糊，画面命令本身冻结，不保留可操作的 Screen。捕获和 teardown 的实际 MC 成本尚未测量。
- 旧 `panel` 桶没有覆盖常驻 HUD。新增独立 `hud` CPU wall 桶，debug 关闭时只做开关判断；每 600 次实际 HUD 绘制报告一次，不混入 panel/GPU/JFR 桶。
- 使用已有 `ScreenLifecycle` JFR event 记录 `PANEL_EXIT_CAPTURE`。它不含后面的 Screen teardown；正常不捕获的路径可能记录 success=false，不能一概解释成异常。

## 为什么这次不直接裁剪 AtomLib 状态

实际桥负责 GL 状态保护、Skia 上下文归一与提交。新 HUD 的常驻调用也会支付这笔边界成本。已有源码明确保留全部 Skia 可触及纹理单元，实验性裁剪不能证明在光影、第三方着色器与多采样器下无泄漏；本轮没有以缩减保护范围或降低模糊刷新率换取数字。

`PageTransitionComposite` 的命令录制、多层透明合成与卡片自身动效仍是过渡成本候选；上轮受控 Raster 对照未证明稳定录制本身有显著额外成本。本轮按用户选择保留切页手感，没有使用整页长期冻结或关闭动态图的替代方案。

下一次 CCB 验收应固定同一分辨率、5× GUI、光影、视角和页面，对照候选前后 HUD 常驻、稳态、开屏、关闭触发帧、退场与切页，观察整帧及 CPU/GPU 分项。已有日志先用完；如自然复测仍卡，再依据新增 HUD/JFR 样本决定具体修改。当前不宣称该实机验收已完成。
