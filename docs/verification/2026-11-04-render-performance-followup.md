## Review follow-up: Python launcher and nested panel accounting

`ProfileWiringIntegrationTest` now probes `python3`, `python`, and `py -3` in the same order and with the same exit-code/`Python` version-output requirements as `gradle/atomchat-layers.gradle`. The selected command retains all arguments. The Python child receives `JAVA_HOME=System.getProperty("java.home")` from the actual test JVM, and the probe prints that value; the test asserts it. Unit coverage checks priority, fallback and no-candidate failure. An actual Windows PATH containing only `C:/Windows/System32;C:/Windows` had `py -3` available and neither `python` nor `python3`; old code failed with CreateProcess error 2 (`py-only-red.log`), corrected code passed. Parent `JAVA_HOME` was deliberately set to the other JDK and `org.gradle.java.home` selected the test JDK: XML captured `py -3` with JDK 17.0.18 on Forge and JDK 21.0.11 on Fabric/NeoForge.

Actual `SkiaGraphics.drawPanel` nested inside a panel facade reproduced `FrameProfile panel n=2` while `FrameSegments frames=1` (`nested-panel-red.log`). `SkiaGraphics` now submits a `FrameProfile` frame only if the corresponding segment ID is nonzero. A second real-facade probe discovered that the nested panel's surface label leaked into the outer frame (`nested-surface-red.log`); the prior label is now restored on normal and exceptional exits. The probe runs the actual official/Fabric `SkiaGraphics`, actual `NotificationHudOverlay`, and actual profile classes against test-only Minecraft/GL stand-ins, including nested HUD, successful nested panel and throwing nested panel (`nested-success-failure-green.log`). This does not assert that Minecraft allows nested bridge draws; it validates the instrumentation boundary under simulated nesting.
