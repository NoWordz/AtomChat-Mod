## 0. 一句话结论

P0-A **确实生效，但只修了开合瞬间的长帧**；稳态主指标几乎未变，与用户「效果提升不大」的主观感受精确吻合。
严格回答「是否无法继续优化」：**否**，仍有三条未修长帧源和集中的稳态热点。但继续堆无损优化不是通往 400 FPS 的最短路径——**日志给出的算术说明应该先做归零对照实验**。
本轮同时纠正一个上一轮的错误预期：**P1 的 GPU 计时绝对值不可信**，末段出现与 CPU 指标背离的未解释 10× 阶跃，不得用来算 400 FPS 预算。

## 7. ⚠️ 必须纠错：P1 的 GPU 计时绝对值不可信

| 观察 | 数据 |
| --- | --- |
| 前 116 窗 | `gpu_panel p50` 1.46–2.60 ms，与 `BLUR` 段（0.20–0.32 ms CPU）共存 |
| 10:57:35–10:57:40 阶跃 | idx115 1.4588 → idx116 **0.5082**（同窗 `p95=9.55 ms` 异常）→ idx117 **0.1445** → 末窗 0.1663 |
| **反证「面板关闭所以 GPU 变轻」** | 阶跃期间 `BLUR` 段**仍在跑**（0.219–0.229），CPU `panel p50` 反而从 1.67 **升到 4.04 ms** |
| 降级计数 | `completed=74996 / dropped=0 / expired=2 / skipped=0 / stalled=0` —— 不是 query 冲突或丢失路径 |
| 实现 | `GlGpuTimer` 用 `GL_TIME_ELAPSED`；query 区间 = `SkiaGraphics.draw` 的 `FrameSegments.begin`（`SkiaGraphics.java:40`）到 `finish`（`:87`，finally 内）；`FrameProfile.frame` 与日志打印在其后 |

`BLUR` 分段在最后 3 窗才消失，比 GPU 阶跃**晚约 12 秒**，两者不同步。10:57:39–10:57:49 有密集点击、页面从 settings→navigation→chat、10:57:47 发送 1053×1080 图片消息（L4698–4703），合理怀疑是走了不同的 `bridge.drawFrame` 路径或 query 区间未覆盖 Skija flush，导致 CPU 侧文字/图片布局变重而 query 内 GL 命令骤减。

**结论**：
- **本轮不得用 `gpu_panel` 绝对值断言「背景模糊 GPU 成本 1.5 ms」**，不得据此算 400 FPS 预算，也不得把 0.13 ms 当「模糊已不花 GPU」。
- P1 的 `pageKey` / `page_phase` / 首开标志 / 降级计数**可用且有价值**；GPU 绝对值需先复核 query 区间是否覆盖 Skija flush 与多 surface 路径，建议下次验收同时记录操作时间轴。
- 上一轮把 P1 表述为「终于能看第一份游戏内 GPU 时间」是**过度承诺**，此处更正。

## 8. 400 FPS 的算术（只用可信的 CPU / interval 下界）

- 400 FPS → **2.5 ms/帧**
- 本次 `chat_interval p50 = 3.09 ms` ≈ **323 FPS**
- 其中 AC 面板 CPU 渲染 `chat_render p50 = 1.89 ms` → **非 AC 部分约 1.20 ms**（MC 本体 + 其余 215 个 mod + GPU 同步）
- 若 AC 渲染归零，理论上限 ≈ 833 FPS；要达 400，AC 预算只剩 **1.30 ms**，即在 1.89 ms 上再降 **31%**
- 稳态可无损动的最大两块：`BRIDGE` 0.76 ms + `LIST` 0.24 ms ≈ 1.00 ms；即便**全部 100% 消除**（不现实），总和 2.09 ms ≈ 476 FPS，且完全忽略 GPU 侧约束
- **`DOTS` 0.744 ms 是最大的单块，但属视觉元素，当前约束下不能删**

**所以：继续无损优化能改善，但单靠它们「稳定 400」概率低；非 AC 的 1.20 ms 是环境地板，AC 再优化也动不了。**
这条算术正是用户「做个归零实验看瓶颈在不在渲染」直觉成立的理由——而且说明**实验应该提前做**，而不是等几轮优化撞墙后再做。

## 9. 对「照抄 Muonium 实验版」的评估

**逻辑成立**：归零对照，一次判定瓶颈是否落在 AC/Lib 渲染，是定位环境地板最干净的方法。

**但实现路径有两个问题**：
1. Muonium 的「稳定」来自**视觉取舍**——开合动画期关闭液态玻璃改画实色（`GlassLook.java:151`）、静态背景冻结、背景采集限 30 Hz、允许借用最多落后 8 个采集代的旧模糊档；它同样每帧清空重画、没有整页缓存。照抄必然动视觉，与 11-05 用户拍板的「视觉不动」冲突，且与 `NotificationRenderWiringTest.java:46-52`（断言 `boolean full = true`、禁止 `BlurMotionGate`）、`docs/HANDOFF-panel-performance-codex.md:190` 直接冲突。
2. 照抄整套 UI 渲染框架工程量大，且引入「不同框架 / 不同页面 / 不同资源」的新变量，**反而无法干净归因**：测出来还掉帧，说不清是环境地板还是新代码。

**更干净的等价实验（建议）**：在**同一个包**里加一个 `debug`-only 三档旁路开关，用户一次启动切档、同一份 `latest.log` 对比：

| 档 | 内容 | 回答的问题 |
| --- | --- | --- |
| A | 完整（现状） | 基线 |
| B | 只关背景模糊 pre-pass，保留全部 UI 绘制 | 毛玻璃占多少 |
| C | 整个面板绘制旁路，只留 MC 本体 | **这个 216-mod 环境下 400 FPS 是否物理可达** |

- 若 **C 都上不了 400** → 直接证明瓶颈不在 AC/Lib 渲染，后续不必再堆渲染补丁；
- 若 **C 能上 400 而 A 不能** → 差值就是 AC 渲染的可回收预算，按 §5 的段开销定点修，不再猜。

同包、同环境、同日志、一个开关可逆，归因比换框架干净得多，工作量也从「重写渲染」降到「加一个旁路分支」。

## 10. 结论与待拍板

1. **「无法继续优化」不成立**：三条长帧源（首开字体同步、emoji 首次栅格化、字多设置 tab）仍在；稳态 `BRIDGE` 0.76 ms 与 `DOTS` 0.744 ms 是明确热点。
2. **但继续堆无损优化不是通往 400 的最短路径**，§8 的算术说明归零实验应提前做。
3. **P1 的 GPU 绝对值本轮作废**，需先复核 query 区间；按页面 CPU 拆分可用。
4. 待用户拍板：实验形态（三档旁路 / 真照抄 Muonium / 先修长帧）、实验期是否允许临时改变视觉（仅诊断、不改产品默认）、以及三条长帧是否同时修。
