# 2026-11-06 三档归零实验 · 真机结果分析

**性质**：只读日志分析 + 结论。未改生产代码、未重新部署、未启动游戏、未 commit/push/发布。
**前序**：`docs/verification/2026-11-06-truth-test-log-analysis.md`（上一轮日志）、`docs/verification/2026-11-06-truth3-mode-experiment.md`（实验包设计）。

## 0. 结论（方向性翻转）

1. **C 档 401.4 FPS → 400 帧在当前环境物理可达，瓶颈确实在 AC/Lib 渲染内**。上一轮「非 AC 的 1.20ms 是环境地板、继续优化够呛」的推断被证伪：那 1.20ms 里有大半是 AC 渲染自身或由它引发的开销。
2. **A→C 可回收 0.423ms**；其中 **A→B（背景模糊 pre-pass）= 0.239ms，占 56%**；B→C（其余面板绘制）= 0.184ms，占 44%。
3. **A−B 的成本不在 GPU 执行时间，而在 CPU 侧 GL 状态同步**：`gpu_panel` 对 A/B 完全不敏感（0.1256 / 0.1259ms），与上一轮离屏「GL scope 0.5ms 纯 CPU、GPU 0.0002ms」吻合。这给出了一个**完全不动视觉**的定点修复靶子。
4. 用户主观「部分页面提升小、部分提升大」——**按页面拆不出显著差异**（四页 A→B 均 0.181–0.213ms）；差异实际落在**轮次/时刻**（0.095–0.306ms），与 A 档自身 1.240ms 的大波动同源。不是页面固有属性。

## 3. ⚠️ C 档是被帧率锁顶住的，不是真实天花板

C 档 11 个窗口的 FPS 依次为 `400.3, 400.8, 401.2, 401.3, 401.3, 401.4, 401.5, 401.5, 401.7, 402.4, 402.5`，**全距仅 2.2 FPS、帧间隔标准差 0.0038ms**——这不是自然波动，是撞上用户锁定的 400 帧上限的典型特征。

**含义**：
- 环境地板 **≤ 2.484ms**，真实值**可能更低**；本报告所有「可回收预算」都是**下界**。
- 因此「A→C 只有 0.423ms」偏保守；若临时解除帧率锁重测 C，真实余量可能明显更大，400 的稳定余量也更宽松。
- 反过来说，正因为 C 卡在 401，**「稳定 400」几乎零余量**：A 需降到 ≤2.50ms，即从 2.914ms 回收 ≥0.414ms 才刚触线；要真正稳住还需更多余量。

**四页差异只有 0.032ms，统计上分不开。** 毛玻璃是整块背景预通道，成本与「当前是哪个页面」基本无关，符合代码结构。

### 4.2 按轮次（同一页面组各测一遍）

| 轮 | 涉及页面 | A | B | A−B |
| --- | --- | --- | --- | --- |
| 0 | other | 3.079 (325) | 2.822 (354) | **+0.256** |
| 1 | navigation / other / settings | 2.871 (348) | 2.690 (372) | +0.181 |
| 2 | navigation / profile | 2.893 (346) | 2.587 (387) | **+0.306** |
| 3 | profile / settings | **2.660 (376)** | 2.565 (390) | **+0.095** |
| 4 | settings | 2.904 (344) | 2.662 (376) | +0.242 |

**轮次差 0.095–0.306ms（3.2 倍）**，而轮 3 的 A 档本身异常快（2.660ms / 376 FPS）——说明差异来自**轮次开始时的系统热状态 / 前序操作残留**，不是页面固有属性。

## 5. 成本归因：A−B 的 0.239ms 在哪

### 5.1 反证「GPU 模糊计算是瓶颈」

| 档 | `gpu_panel` p50 中位（4096 混窗，仅作量级旁证） |
| --- | --- |
| A | 0.1256 ms |
| B | **0.1259 ms**（几乎不变） |
| C | 0.0946 ms |

**A 有 pre-pass、B 完全没有，GPU 计时却纹丝不动**；只有把整个 `drawPanel` 旁路（C）才降。两条可能解释，都指向同一结论：
1. `GL_TIME_ELAPSED` 区间未覆盖 pre-pass 的 GL 命令（上一轮已怀疑 query 区间/flush 覆盖问题）；
2. 或 pre-pass 的 GPU 执行本就很短，成本在 **CPU 侧提交与同步**，GL_TIME_ELAPSED 不计。

无论哪条，**A−B 的 0.239ms 都不能靠「优化模糊 shader / 降分辨率 / 减 pass」收回**，那会白做且动视觉。这也进一步坐实上一轮「P1 GPU 绝对值不可信」的纠错：它对一个已被 A/B 证明存在的 0.239ms 真实成本完全不敏感。

### 5.2 代码证据：每帧 CPU 侧 GL 同步点

`platforms/1.21.1-fabric/src/main/java/com/atom/chat/render/PanelBlurRenderer.java`：

| 行 | 调用 | 性质 |
| --- | --- | --- |
| `:102` | `GL30.glGetInteger(GL_FRAMEBUFFER_BINDING)` | **同步查询** |
| `:104` | `GL30.glGetIntegerv(GL_VIEWPORT, …)` | **同步查询** |
| `:105` | `GL30.glIsEnabled(GL_SCISSOR_TEST)` | 状态查询 |
| `:145-159` | 恢复 FBO / viewport / scissor，且 GL 与 `GlStateManager` **双写** | 状态往返 |
| `:168` | `GL11C.glGetError()` | **同步查询（每帧）** |
| `:384-385` | blit 前后绑定 READ/DRAW framebuffer | 绑定往返 |
| `:450-455` | 又一组 `glGetInteger` + `glGetIntegerv` + `glIsEnabled` + disable scissor | **同步查询** |

`glGet*` / `glGetError` 是管线同步点，会造成 CPU 等待或气泡，**是纯 CPU 成本、不计入 GPU 完成时间**。与上一轮离屏受控测得的「GL 状态保存/恢复固定约 0.5ms，GPU 仅 0.0002ms」量级吻合（游戏内实测净效应 0.239ms）。

**这就是 A−B 的主要来源，也是下一步唯一「无损、不动视觉、收益最大」的靶子。**

### ⚠️ 三条必须说清的校准（不许把离屏值当 FPS 收益）

1. **离屏只省 0.0375ms，真机 A−B 是 0.239ms** —— 差 6 倍。离屏是空 GPU 队列，`glGet*` 的同步代价在真机满队列下可能被放大，但也可能仍然只占小头。**P0-C 不能宣称「收回 0.239ms」**；剩余约 0.20ms 很可能落在 pre-pass 的全分辨率背景采集/blit、5 pass 的 CPU 提交、或 GPU 隐式同步上，尚未定位。
2. **`glGetError` 门控在本次验收配置下不生效**：`errorCheckDue()` 在 `config.debug=true` 时恒返回 true（源码 `:183-188`），而 CCB 实例 `debug` 本来就是 `true`。因此这项削减的收益在产品默认（debug=off）才成立，**真机验收时不要指望它**。
3. **离屏 GPU 时间 0.0062ms ≪ 真机 A−B 0.239ms**，再次印证离屏空场景无法复现游戏内 GPU 队列拥塞；也再次说明 §5.1 的「GPU 计时不可信」结论。

**内置对照判据（供统一真机验收）**：修复若有效，**A 档应向 B 档靠拢，而 B 档基本不变**（B 本就跳过 pre-pass）。若 A 无明显变化，即证伪「`glGet*` 是 A−B 大头」这一假设，应转向给 pre-pass 加真机分段计时，而不是继续盲改。
