## 五项实机问题

1. 服务端输入严重掉帧；历史保留天数输入没有相同问题。
2. 设置数值框比服务端框宽大、单位在框内。用户认可服务端紧凑尺寸及框外单位方向，但不认可其整体实现。
3. 卡片间距、分组栏、折叠动效和tab退出/进入流程未复用当前设置页。不能将使用相同材质与token冒充统一前端。
4. 消息格式文本相对边框下沉，内边距和光标定位计算需要统一。
5. 旧预览与实机条件、候选版本不同，审查没有明确区分。离屏绘制不能代替实际面板前端验收。

## 当前源码证据，非性能实测结论

- `ServerConfigPage.key` 每个聚焦输入的按键都会求值 `host.clipboard()`，再传入字段处理，即使不是粘贴。平台桥直接读Minecraft系统剪贴板。历史数字输入没有此路径。这是明确的不必要系统调用，但尚未采样确认其占全部掉帧的比例。
- `SettingsFormField.paint` 每帧重算分行；多行按递增子串测宽，不能假设长文本成本低。需要有实际输入长度、布局失效条件和耗时验证。
- `SettingsFormField` 多行首行中心使用 inset10+lineHeight22/2=21，而格式框只有32高、中心16，形成5单位向下偏移。默认只显示一行的格式框仍走多行计算。
- `ServerConfigPage` 折叠用自己的 `UiMotion.approach(...HOVER_MS)`，现有设置用 `expApproach(...GROUP_FOLD_TAU_MS=50)` 和共享行几何。tab点击只改chips并markEntered，需接入设置当前完整的外层离场合成流程。
- 当前设置子页局部selectChip也markEntered，不能据此断言设置没有退出；真正退出由 `PageTransitionComposite` 及宿主bodyVariant驱动，必须追完整调用链。
- 图四来自 `build/v090-visual-correction`，实际部署来自 `build/v090-list-editor-review`。预览测试使用新建默认配置/纯色surface，关闭动画，手工绘制header；未经过游戏真实背景与完整合成链。后续交付必须清楚标明离屏图和实机图，并给同一候选同条件的对照，不能继续拿此类静态图证明动效或性能。
