**这直接推翻了我若按「全场合并中位」得出的 A−B = 0.098ms** —— 那个数被热身窗和末端漂移污染了。

### 4.1 正确做法：用「相邻配对」抵消漂移

A 与 B 在每轮里**时间紧邻**（相隔约 10 秒），配对相减几乎不受漂移影响：

| 配对 | A | B | A−B |
| --- | --- | --- | --- |
| seg1→2 | 3.730 | 3.010 | +0.720（**热身，不计**） |
| seg5→6 | 2.984 | 2.751 | **+0.233** |
| seg9→10 | 2.770 | 2.574 | **+0.196** |
| seg13→14 | 2.729 | 2.582 | **+0.147** |

→ **A−B = 0.147 / 0.196 / 0.233，均值 0.192 ms**，三次同号同量级。这与前几轮的 0.239 / 0.288 同量级，**比合并中位的 0.098 可信得多**。

**D 的预期位置**：30Hz 在 360fps 下只有 8.3% 的帧真刷新，故 `D ≈ B + 0.083×(A−B) ≈ B + 0.016`。第 2/3 轮实测 D = 2.631 / 2.652，对 B = 2.751 / 2.574、A = 2.984 / 2.770 —— **落在 B 与 A 之间、贴近 B**，与预测一致（偏差 0.06–0.08，在漂移噪声内）。

> 第 4/5 轮 D（2.870 / 3.037）比同轮 A 还慢，是因为那两轮正好落在漂移的慢尾巴上，不是 D 变慢。**这正是「顺序走 A→B→C→D 一次」这个协议无法分辨 <0.4ms 差异的证据。**

## 6. 结论与判定

按你定的判据（「照抄 Muonium 后仍不稳 ⇒ 问题不在渲染」）：

1. **照抄之后稳了**（D 抖动 0.546 ≈ B 0.594 ≪ A 1.594）⇒ **不稳的原因确实在 AC 的渲染路径上，具体是「每帧重算背景模糊」**。这条假设**成立**，可以结案。
2. **但 400 不是靠这条策略能到的**：D 稳态 361.6，比 A 的 350.2 高 11 FPS，离 400 还差 ~38 FPS。剩下的不是模糊，是**整块面板每帧重绘**（`DOTS` + `BRIDGE` + `LIST`）。
3. 顺带纠正上一轮我给你的「A−B = 0.239ms 占 A−C 56%」这类比例：本轮配对 A−B ≈0.19ms，而 A−C ≈0.36–0.49ms，模糊约占**四成**。跨会话绝对值会变，**别把某一轮的比例当常数**。

## 7. 下一步建议（等你拍板）

**协议先改**：下次别再「顺序走 A→B→C→D 一次」。改成 **ABAB / ADAD 交替、每档 10–12 秒、走 4–6 个来回**，用**相邻配对**求差；同时**把 400 帧锁临时放开**（或换一个天然低于 400 的场景）让 C 档重新具备漂移可见性，否则 C 永远是「盲基准」。

**技术上，靶子已经换了**：从「模糊」换到「画面板本身」。把 tuui 调研的结论接上（`docs/verification/2026-11-06-tuui-render-research.md`）：

- 聊天框**不在 tuui 里**，在 `chatcore` + ModernUI 3.12 上；tuui 自己**没有** layout 缓存、每帧逐字 measure，它稳是因为画得少。真正值得抄的是 chatcore/ModernUI 的**「整页一张 GPU 层纹理 + 脏区才重录」**。
- 对应 AC：把面板静态层（底板/圆角/边缘点阵/静态文字）烘成一张纹理，每帧只合成 1 个 quad + 画动态层；**不改视觉**。这正好打 `DOTS 0.598` 与 `DRAW 0.827`。

**不推荐**当下就做「模糊 5 pass → 2 pass」（改视觉）或「面板直画主 FBO」（拆 AtomLib 桥，风险高）——前者你已经定过不动视觉，后者等前两项做完还不达标再评估。
