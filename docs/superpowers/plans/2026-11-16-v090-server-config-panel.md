## 2. 当前代码事实

- 三端命令由 `ConfigScreenServer` 注册，`/atomchat gui` 发 Snapshot，内容为配置版本、`ServerConfigValues` 和资源包状态。当前命令门槛为多人 OP 等级 2，单人主机允许编辑；没有用户要求改变该权限策略。
- official `ConfigScreenClient.onSnapshot` 和 Fabric `openScreen` 会新建 `ServerConfigScreen` 并调用 `setScreen`，所以当前确实没有使用 AtomChat 主面板导航。
- 旧 `ServerConfigScreen` 使用原版按钮和文本输入，按独立屏幕尺寸排列；保存成功后回 parent。不能只套一层新背景就称整合完成。
- `ServerConfigValues` 是当前页面、线协议和服务端校验共用的配置结构，包含托管、资源包和常用语字段，优先保持这个单一事实来源。
- 现有 `Snapshot` 带配置版本和配置值，`Save` 带版本和草稿值。当前成功 `Result` 只给成功标志/错误，服务端保存后递增版本；旧界面成功即关闭，所以连续留页保存需要补齐最新确认状态。
- 资源包 `Refresh/Status` 只重扫并更新包摘要，不回传整份配置；这条行为本来就用于避免覆盖未保存编辑，必须保留。
- 当前客户端 `SettingsItem.set` 会立即保存 `AtomChatConfig`。服务端页面可以复用外观和交互，但不能直接复用这个写入绑定，更不能把服务器草稿保存到客户端配置文件。
- 现有 `SettingsSectionPage` 已有数值输入行和编辑交互；`SettingsDetailPage` 已处理固定头栏、分类切换、每分类滚动记忆、模态及滚动条。优先复用这些先例，不照抄旧屏幕的固定像素双列布局。
- `SettingsHomePage` 直接枚举 `SettingsSection.values()` 生成首页卡片。服务端配置应有独立的非根导航页和会话，不直接加入这个枚举，避免违反“不增加首页入口卡片”的决定；复用设置页视觉不等于复用客户端设置分类的数据绑定。

这些为源码阅读事实，没有启动客户端或配置服务器。

- 渲染继续走当前主面板及现有设置页路径，不换 UI 框架，不因共享技能的通用默认路线引入新的依赖或渲染层。
- 从现有 `UiTokens`、`UiCards`、`ShellHeader`、`HeaderChrome`、`SettingsGroupIcons`、`SettingsGroupGlyphs` 及对应设置行获取样式和几何，不独立拍一套颜色、圆角、阴影、字号或间距。
- 顶部标题和返回按钮固定；分类 chip 使用当前设置页的布局、选中、hover、press 与动效。分类下方设置列表滚动，底部保存条占用明确布局区域，不盖住最后一行。
- 切换分类保留草稿和各分类滚动位置，焦点与输入状态遵循现有设置页约定，不在输入数字时重复接收 key/char 导致双写。
- 常规保存使用主题强调色。放弃未保存改动的确认复用现有警告弹窗、红色警告/确认及灰色取消，不给普通保存套危险色。
- 同一按钮家族使用现有尺寸与点击区。图标从现有 SVG/图标接口中按含义选择；缺失时再新增手写 SVG，遵循 token 尺寸和 tight bounds 居中，不用 emoji、临时字符或图形占位代替成品。
- 页面跟随已有主题、面板尺寸、GUI scale 和现有动效；中英文、长字段说明及窄面板的布局仍需后续真实渲染检查。
- 本轮不新增“恢复全部”“清空缓存”“解析器正则编辑器”等未经讨论的操作，不扩成通用服务器管理台。

## 4. 内容与交互

| 分类 | 现有内容 | 交互要求 |
|---|---|---|
| 托管 | 托管开关、单文件限制、媒体总量、头像总量、保留天数、上传冷却 | 复用设置开关/数值输入行，展示现有单位和有效范围，编辑只改草稿 |
| 资源包 | 包功能开关、文件数/体积限制、名称、包状态、重扫 | 复用现有行/输入；重扫只更新包状态，不能覆盖名称、限额或其他未保存值 |
| 常用语 | 现有服务端常用语列表、添加、编辑、删除 | 使用现有列表和输入/弹窗先例，保留当前条数与长度约束；列表变化归入同一份草稿 |

全页只有一份编辑基准与草稿。保存操作提交全部分类的最终草稿，不因当前 chip 隐藏而漏掉其他分类的改动。

保存流程：

1. 本地使用共用规则校验，并将错误定位到字段；不能只显示“出错了”而丢失输入。
2. 发送当前配置版本和草稿，显示保存中，阻止重复提交；提交期间输入/离开行为以不丢失草稿、不产生不明并发为准。
3. 服务端按当前连接的编辑资格、配置版本和字段规则裁定写入；页面可见性不是授权依据。实现时核对当前接收端是否确实逐次执行权限校验，缺失则在受影响配置链路补齐并验证。
4. 成功时接收服务端实际持久化的规范化值、最新版本及必要状态，更新编辑基准、清除已确认 dirty，停留原 chip；普通成功反馈复用现有提示组件。
5. 失败时保留草稿与原编辑基准，显示原因。版本冲突不能自动覆盖他人修改，权限撤销不能继续伪装可保存。
6. 若因断线或迟到回复无法确认结果，不伪报成功；配置会话与当前服务器/连接绑定，不让旧连接回复修改新服务器页面。

实现可补充必要的版本/确认值回传或等价受控刷新，优先复用已有快照能力。协议变化应明确新旧端行为，不能让保存后的快照被误当成一次新的命令打开请求，也不能用旧草稿覆盖服务端规范化结果。

离开流程复用现有确认弹窗：没有改动直接回聊天页；有未保存改动时确认放弃或继续编辑。放弃只丢本次服务端配置草稿，不清聊天草稿、历史、个人素材或学习数据。
